# Requirements Document

## Introduction

`/ui/items` ライブラリ画面では、カードへのタグ付与に編集モード（単一アイテム編集画面）を
開く必要があり、複数アイテムを整理する際の操作コストが高い。サイドバーのタグ一覧へカードを
ドラッグ&ドロップするだけでタグを付与できれば、整理作業が直感的かつ短い動線で完結する。

本要件は、ライブラリ画面のカードを起点に「カードをサイドバーのタグ要素へドロップして当該タグを
付与する」操作を、既存のタグ付与エンドポイント（新規 API を追加しない）の上に重ねる形で導入する。
既存の絞り込みトグル（#117）・アクティブフィルタチップ（#115）・一括選択 UI（#118）・状態タブ
（#119）の挙動を破壊しないことを前提とし、JS 非対応環境では従来の編集経路でタグ付与可能な
プログレッシブエンハンスメントとして提供する。

## Requirements

### Requirement 1: カードからタグ要素へのドラッグ&ドロップ付与

**Objective:** As a 一覧画面でアイテムを整理するユーザー, I want カードを掴んでサイドバーのタグ要素にドロップするだけでタグを付与できる, so that 編集モードを開かずに直感的な操作でタグを整理できる

#### Acceptance Criteria

1. The Items UI shall ライブラリ画面（`/ui/items`）の各アイテムカードを、ポインタ操作で掴んで移動できるドラッグ可能要素として提供する
2. The Items UI shall サイドバーのタグ一覧の各タグ要素を、カードのドロップを受け付ける要素として提供する
3. When ユーザーがカードを掴みサイドバーのタグ要素にドロップしたとき, the Items UI shall 当該カードが表すアイテムに、ドロップ先タグ要素が表すタグを付与する
4. When カードからタグ要素へのドロップによるタグ付与が成功したとき, the Items UI shall 当該カードのタグ表示に付与されたタグを反映する
5. If ユーザーがカードをタグ要素以外の領域（ドロップ対象でない位置）にドロップしたとき, the Items UI shall いかなるタグ付与も実行しない
6. While ユーザーがカードのドラッグを開始してからドロップまでの間, the Items UI shall 既存の状態タブ・タグ絞り込みトグル・アクティブフィルタチップ・検索クエリ・ソート・ページ送りの設定を変更しない

### Requirement 2: タグ付与の永続化と冪等性

**Objective:** As a タグを付与したユーザー, I want 付与したタグが永続化され、同じタグの再付与でも壊れない, so that 整理結果を信頼してリロードや再操作ができる

#### Acceptance Criteria

1. When カードからタグ要素へのドロップによるタグ付与が成立したとき, the Items Service shall 既存のタグ付与エンドポイントを介して当該タグ付与を永続化する
2. When タグ付与の永続化が成功したアイテムを含む一覧をユーザーがリロードしたとき, the Items UI shall 付与済みのタグを引き続き表示する
3. When ユーザーが既に当該タグを保持しているアイテムのカードを同じタグ要素にドロップしたとき, the Items UI shall 当該アイテムのタグ集合を重複なく維持する（同じタグを二重に追加しない）
4. If ユーザーが既に当該タグを保持しているアイテムのカードを同じタグ要素にドロップしたとき, the Items Service shall タグ付与をエラーとせず、成功として扱う
5. The Items Service shall カードからタグ要素へのドロップによるタグ付与に既存のタグ付与エンドポイントを用い、本要件のための新規 API エンドポイントを追加しない
6. The Items Service shall ドロップによるタグ付与に、既存の単一アイテム編集と同じタグ正規化規則を適用する

### Requirement 3: ドラッグ操作のフィードバックと対象範囲

**Objective:** As a ドラッグ&ドロップ操作を行うユーザー, I want どのタグにドロップしようとしているかが視覚的に分かる, so that 誤ったタグへの付与を防ぎながら操作できる

#### Acceptance Criteria

1. While ユーザーがカードをドラッグ中である間, the Items UI shall ドラッグ中であることをユーザーが認識できる視覚的状態を提示する
2. While ドラッグ中のカードが特定のタグ要素の上にある（そのタグへドロップ可能な）間, the Items UI shall 当該タグ要素がドロップ先候補であることを視覚的に提示する
3. When ユーザーがドラッグ操作を中断（タグ要素以外で離す・キャンセルする）したとき, the Items UI shall ドラッグ中およびドロップ先候補の視覚的状態を解除する
4. Where デスクトップのサイドバーのタグ一覧が表示されている環境, the Items UI shall 当該サイドバーのタグ要素をドロップ先として提供する
5. Where 同一のタグ一覧がデスクトップのサイドバーとモバイルのボトムシートに重複描画される環境, the Items UI shall いずれのタグ一覧へドロップしても同一のタグ付与挙動を提供する

### Requirement 4: タッチデバイス向け代替手段

**Objective:** As a タッチデバイスを使うユーザー, I want ドラッグ&ドロップが困難な環境でもタグを付与できる, so that デバイスを問わず同じ整理操作が行える

#### Acceptance Criteria

1. Where ポインタによる正確なドラッグ&ドロップが利用できないタッチ環境, the Items UI shall カードへのタグ付与を行う明示的な代替手段を提供する
2. When ユーザーがタッチ環境の代替手段でアイテムにタグを付与したとき, the Items UI shall デスクトップのドロップ付与と同一のタグ付与・永続化・冪等性の挙動を提供する
3. The Items UI shall タッチ環境の代替手段によるタグ付与に、本要件のための新規 API エンドポイントを追加せず既存のタグ付与エンドポイントを用いる

### Requirement 5: 異常系の扱い

**Objective:** As a タグ付与操作を行うユーザー, I want 通信失敗や認可エラー時に整理結果が壊れない, so that 失敗を認識して安全に再操作できる

#### Acceptance Criteria

1. If ドロップによるタグ付与の永続化が通信失敗・サーバエラーで完了しなかったとき, the Items UI shall 当該カードのタグ表示を付与成功状態に変更しない
2. If ドロップによるタグ付与の永続化が失敗したとき, the Items UI shall ユーザーが付与に失敗したことを認識できる通知を提示する
3. If ユーザーのセッションが失効した状態でドロップによるタグ付与が試行されたとき, the Items Service shall 当該アイテムへのタグ変更を実行しない
4. The Items Service shall ドロップによるタグ付与の対象を、操作ユーザーが所有するアイテムに限定する
5. If ドロップによるタグ付与のリクエストに操作ユーザーが所有しないアイテム識別子が含まれていたとき, the Items Service shall 当該アイテムへのタグ変更を実行せず、ユーザーに失敗を通知する

## Non-Functional Requirements

### NFR 1: 既存 API のみの利用

1. The Items Service shall カードからタグ要素へのドロップおよびタッチ代替手段によるタグ付与の双方で、既存のタグ付与エンドポイントのみを用い、本要件のための新規 API エンドポイントを追加しない
2. The Items Service shall 既存のタグ付与エンドポイントのリクエスト／レスポンス契約を本要件導入後も変更しない

### NFR 2: プログレッシブエンハンスメント

1. The Items UI shall JavaScript を無効化または非対応のブラウザ環境で、本要件導入前と同等の一覧閲覧・単一アイテム編集経路によるタグ付与の動線を維持する（ドラッグ&ドロップ UI そのものは JS 必須として未提供で構わない）
2. The Items UI shall 本要件導入後も、Issue #117 で導入されたカード上タグのクリック絞り込みトグルの挙動を変更しない
3. The Items UI shall 本要件導入後も、Issue #118 で導入された一括選択 UI（カードの選択チェックボックス・選択ツールバー・一括タグ付けダイアログ）の挙動を変更しない
4. The Items UI shall 本要件導入後も、Issue #115 で導入されたアクティブフィルタチップの可視化と解除動線の挙動を変更しない

### NFR 3: ユーザー可視のレスポンス品質

1. When ユーザーがカードをタグ要素にドロップしたとき, the Items UI shall タグ付与処理を開始したことを示す視覚的フィードバックを 300ms 以内に提示する
2. When ドロップによるタグ付与が成功したとき, the Items UI shall 単一アイテムへの付与において、操作完了の視覚的反映（カードのタグ表示更新）を 1 秒以内に開始する

### NFR 4: アクセシビリティ

1. The Items UI shall ドラッグ&ドロップを唯一のタグ付与手段とせず、ドラッグ&ドロップを利用できないユーザー（キーボード操作・タッチ環境）に対しても、既存編集経路またはタッチ代替手段によるタグ付与の動線を提供する
2. The Items UI shall ドロップ先となるタグ要素を、色のみに依存せず識別可能な形（テキストラベルを含む）で提供する

### NFR 5: 可観測性

1. The Items Service shall ドロップによるタグ付与の実行について、既存のタグ付与エンドポイントが行う構造化ログの粒度を維持し、トークン／Cookie／OAuth 生レスポンスの生値を出力しない

## Out of Scope

- 複数カードをまとめて 1 操作でドラッグ&ドロップしてタグ付与する機能（Issue #118 の一括操作で扱う）
- タグの並び替え UI
- ドラッグ&ドロップ操作によるタグの新規作成 UI（存在しないタグへのドロップでタグを生成する挙動）
- カードからタグ要素へのドロップによる「タグ削除」「タグ置換」操作（本要件は付与のみを対象とする）
- ドラッグ&ドロップによるアイテムの状態変更（read / archived 等）やアイテム間の並び替え
- Chrome Extension（拡張機能）側および MCP 経由でのドラッグ&ドロップ UI / API 公開
- アクティブフィルタチップやカード上タグボタンをドロップ先とする操作（ドロップ先はサイドバー／ボトムシートのタグ一覧に限定する）

## Open Questions

以下は Issue 本文を唯一の真実として要件化した結果、仕様として確定しきれなかった判断点である。
いずれも「実装方針の選択」に属し、Developer / Architect が AC（特に Requirement 2 の冪等性、
Requirement 4 のタッチ代替手段）を満たす範囲で判断してよい。仕様面で誤読されない最小限の
方針のみ示す。

- **(a) タッチ環境の代替手段の具体 UI（Requirement 4.1）**: Issue 本文は「長押しメニュー等」と
  例示するに留まり、具体形（長押しコンテキストメニュー／カードのタグ追加ボタン／既存編集画面への
  導線強化）は未確定。Requirement 4 の AC（既存エンドポイント利用・付与/永続化/冪等性の同等性）を
  満たせばどの代替手段を採用してもよい。
- **(b) 永続化に用いる既存エンドポイントの選択（Requirement 2.1 / 2.3 / 2.4）**: 既存のタグ付与
  エンドポイントは「タグ集合の全置換型（`PUT /v1/items/{id}/tags`）」と「単一タグの追加型・冪等
  （`POST /v1/items/bulk-tag`、単一 item でも利用可）」の 2 つが存在する。どちらを用いても
  Requirement 2 の冪等性 AC（既存付与済みタグへの再ドロップがエラーや重複にならない）を満たせれば
  よく、選択は Developer の実装判断に委ねる。全置換型を選ぶ場合は、ドロップ前のタグ集合を保持した
  まま当該タグを追加し他タグを失わないことが冪等性 AC の充足条件となる。
- **(c) ドロップ視覚フィードバックの要求レベル（Requirement 3.1 / 3.2）**: 「ドラッグ中であること」
  「ドロップ先候補であること」が視認できれば足り、アニメーション・ゴースト画像・ハイライト色など
  具体的な演出レベルは未確定。最小限の視覚区別（クラス付与によるスタイル変化等）で AC を満たして
  よい。
