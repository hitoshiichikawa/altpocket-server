# Requirements Document

## Introduction

`/ui/items` ライブラリ画面では、カードの削除・タグ付け・アーカイブ等の整理操作が 1 件単位で
しか行えず、棚卸し作業（過去アイテムの一掃、複数記事への横断タグ付与など）が著しく非効率
である。本要件は、ユーザーが一覧上で複数のアイテムを選択し、選択集合に対して「まとめて削除」
「まとめてタグ付け」を 1 操作で実行できるようにすることで、整理動線の操作回数を大幅に削減
することを目的とする。

依存元 Issue #119（read / archived 状態の導入）は既に merge 済み（commit 64c03ae）で、
カードは `unread` / `read` / `archived` の 3 状態を持ち、状態タブで一覧が分割されている。
本要件は、その既存の一覧表示・状態タブ・タグフィルタチップ（#115）・URL クエリ駆動
（#114 / #115 / #117）の挙動を破壊せず、その上に重ねる形で「選択モード」「選択ツールバー」
「一括操作」を導入する。

## Requirements

### Requirement 1: アイテム選択 UI

**Objective:** As a 一覧画面の閲覧ユーザー, I want 一覧上で複数のアイテムを 1 操作ずつ選択できる, so that 棚卸ししたい対象を視覚的に確認しながら束ねられる

#### Acceptance Criteria

1. The Items UI shall 一覧に表示中の各アイテムカードに対し、選択状態を切り替える操作要素を提供する
2. When ユーザーがあるカードの選択操作要素を起動したとき, the Items UI shall 当該カードを選択状態に切り替える
3. When ユーザーが選択状態のカードの選択操作要素を再度起動したとき, the Items UI shall 当該カードを未選択状態に戻す
4. The Items UI shall 選択中のカードを未選択のカードと視覚的に区別可能な形（背景・縁取り・選択操作要素の表示状態のいずれか以上の組み合わせ）で提示する
5. The Items UI shall 選択操作要素を、色のみに依存せずテキストラベルまたはアイコンで識別可能な形で提供する
6. While ユーザーが一覧上で複数のカードを選択する間, the Items UI shall 既存の状態タブ（Unread / All / Archived）・タグフィルタチップ・検索クエリ・ソート・ページ送りの動作を変更しない

### Requirement 2: Shift+クリックによる範囲選択

**Objective:** As a 連続したアイテム群をまとめて整理したいユーザー, I want Shift+クリックで一覧上の連続範囲を一括選択できる, so that 1 件ずつチェックする手間なしに範囲指定で束ねられる

#### Acceptance Criteria

1. While 少なくとも 1 件のカードが選択済みである間, when ユーザーが別のカードの選択操作要素を Shift キーを押しながら起動したとき, the Items UI shall 直前に起動された選択操作要素から当該カードまでの範囲のカードすべてを選択状態にする
2. When 範囲選択操作の範囲内に既に選択済みのカードが含まれていたとき, the Items UI shall それらのカードを選択状態のまま維持する
3. The Items UI shall 範囲選択における「直前に起動された選択操作要素」を、現在の一覧表示順（既存ソート条件下）に基づいて決定する
4. If 範囲選択操作時に「直前に起動された選択操作要素」が存在しない（選択履歴が空である）とき, the Items UI shall 当該クリックを通常の単一選択トグルとして扱う

### Requirement 3: 選択ツールバー

**Objective:** As a 選択操作中のユーザー, I want 選択件数と一括操作ボタンが常時画面上に提示される, so that どの操作が実行できるか・何件に影響するかを毎回確認できる

#### Acceptance Criteria

1. While 少なくとも 1 件のカードが選択状態である間, the Items UI shall 現在の選択件数を含む選択ツールバーを画面上に表示する
2. While 選択中のカードが 1 件もない間, the Items UI shall 選択ツールバーを表示しない
3. The Items UI shall 選択ツールバーに「一括削除」「一括タグ付け」「選択解除」の操作要素を含める
4. When ユーザーが選択ツールバーの「選択解除」を起動したとき, the Items UI shall すべてのカードを未選択状態に戻し、選択ツールバーを非表示にする
5. The Items UI shall 選択ツールバーをスクロール中も選択操作の対象から到達可能な位置に表示する
6. The Items UI shall 選択件数の表示を選択状態の変化に追随させて更新する

### Requirement 4: 一括削除

**Objective:** As a 不要アイテムを一掃したいユーザー, I want 選択中のアイテムを 1 操作でまとめて削除できる, so that 個別に削除を繰り返す手間なしに棚卸しできる

#### Acceptance Criteria

1. When ユーザーが選択ツールバーの「一括削除」を起動したとき, the Items UI shall 削除対象件数を含む確認ダイアログを表示する
2. While 確認ダイアログが表示されている間, the Items UI shall ユーザーが操作をキャンセルできる手段を提供する
3. When ユーザーが確認ダイアログをキャンセルしたとき, the Items UI shall 削除操作を実行せず、選択状態を保持する
4. When ユーザーが確認ダイアログを承認したとき, the Items UI shall 選択中のすべてのアイテムを削除する
5. When 一括削除が成功したとき, the Items UI shall 削除されたアイテムを一覧表示から除去する
6. When 一括削除が成功したとき, the Items UI shall 選択状態をリセットし、選択ツールバーを非表示にする
7. If 一括削除の一部または全部が失敗したとき, the Items UI shall 失敗したアイテムをユーザーが特定可能な形（タイトルまたは URL を含むメッセージ）で通知する
8. If 一括削除の一部が失敗したとき, the Items UI shall 失敗したアイテムを選択状態のまま一覧に残し、成功したアイテムのみを一覧から除去する

### Requirement 5: 一括タグ付け

**Objective:** As a 複数アイテムに同じタグを付けたいユーザー, I want 選択中のアイテムに同じタグを 1 操作でまとめて付与できる, so that 1 件ずつタグ編集画面を開く手間を省ける

#### Acceptance Criteria

1. When ユーザーが選択ツールバーの「一括タグ付け」を起動したとき, the Items UI shall 付与するタグを入力する手段（テキスト入力または既存タグからの選択）を提示する
2. The Items UI shall 一括タグ付けの入力欄に既存の単一アイテム編集と同じタグ正規化規則を適用する
3. When ユーザーが付与するタグを確定したとき, the Items UI shall 選択中のすべてのアイテムの既存タグ集合に、入力されたタグを追加する
4. When 一括タグ付けの結果として既に対象アイテムが当該タグを保持しているとき, the Items UI shall 当該アイテムのタグ集合を重複なく維持する（同じタグを 2 重に追加しない）
5. When 一括タグ付けが成功したとき, the Items UI shall 一覧上の対象カードに、付与されたタグを反映表示する
6. When 一括タグ付けが成功したとき, the Items UI shall 選択状態をリセットし、選択ツールバーを非表示にする
7. If 一括タグ付けの一部または全部が失敗したとき, the Items UI shall 失敗したアイテムをユーザーが特定可能な形（タイトルまたは URL を含むメッセージ）で通知する
8. If 一括タグ付けの一部が失敗したとき, the Items UI shall 失敗したアイテムを選択状態のまま一覧に残し、成功したアイテムは選択解除する
9. If ユーザーが空文字または正規化後に空となるタグを入力したとき, the Items UI shall 一括タグ付け操作を実行しない

### Requirement 6: キーボードショートカット

**Objective:** As a キーボード中心の操作を好むユーザー, I want キーボードだけでフォーカス中のカードを選択トグルできる, so that マウスに持ち替えずに選択集合を組み立てられる

#### Acceptance Criteria

1. While 一覧上のカードがキーボードフォーカスを持つ間, when ユーザーが選択トグル用ショートカットキーを押下したとき, the Items UI shall 当該カードの選択状態をトグルする
2. The Items UI shall 選択トグル用ショートカットキーを、既存ショートカット（`j` / `k` / `o` / `n` / `/` / `?` / `e` 等）と衝突しないキーに割り当てる
3. While 入力欄（検索ボックス・タグ編集欄・確認ダイアログ等の文字入力フォーカス中）にフォーカスがある間, the Items UI shall 選択トグル用ショートカットを発火させない
4. The Items UI shall 選択ツールバーおよびその操作要素を、キーボードフォーカスで到達可能とする
5. When 選択ツールバーの操作要素がキーボード起動されたとき, the Items UI shall マウスクリック時と同じ挙動を実行する

### Requirement 7: 選択状態のライフサイクル

**Objective:** As a 一覧上で選択操作を続けるユーザー, I want 選択状態が予測可能な単位でリセットされる, so that ページ遷移時に意図しない一括操作が誤発火しない

#### Acceptance Criteria

1. When ユーザーが状態タブ（Unread / All / Archived）を切り替えたとき, the Items UI shall 既存の選択状態をすべてリセットし、選択ツールバーを非表示にする
2. When ユーザーがタグフィルタチップ・検索クエリ・ソート・ページ送りで一覧を切り替えたとき, the Items UI shall 既存の選択状態をすべてリセットし、選択ツールバーを非表示にする
3. When ユーザーが画面をリロードしたとき, the Items UI shall 選択状態を空（未選択）から開始する
4. When ユーザーがブラウザの戻る／進む操作で前後の一覧状態に遷移したとき, the Items UI shall 選択状態を空（未選択）から開始する
5. While 一覧フラグメントが非同期で差し替えられた直後, the Items UI shall 選択状態を空（未選択）から開始する

### Requirement 8: 認可・データ分離

**Objective:** As a マルチユーザー環境のユーザー, I want 一括操作の対象が常に自分の所有アイテムに限定される, so that 他ユーザーのアイテムを誤って削除・タグ付けする事故が起きない

#### Acceptance Criteria

1. The Items Service shall ユーザーが他ユーザーの所有するアイテムを一括操作の対象にすることを拒否する
2. If 一括操作のリクエストに認可されていないアイテム識別子が含まれていたとき, the Items Service shall 当該アイテムへの変更を実行せず、ユーザーに失敗を通知する
3. If 一括操作のリクエストに既に存在しない（削除済み等）アイテム識別子が含まれていたとき, the Items Service shall 当該アイテムへの変更を実行せず、ユーザーに失敗を通知する

## Non-Functional Requirements

### NFR 1: ユーザー可視のレスポンス品質

1. When ユーザーが選択操作要素を起動したとき, the Items UI shall 選択状態の視覚反映および選択ツールバーの件数更新を 200ms 以内に開始する
2. When ユーザーが一括削除または一括タグ付けを起動したとき, the Items UI shall 100 件以下の選択件数において操作完了の視覚的フィードバック開始を 1 秒以内に提示する
3. While 一括操作の結果反映中である間, the Items UI shall 現在表示中の一覧カードを空状態で置き換えてちらつかせる挙動を発生させない

### NFR 2: 範囲・上限

1. The Items UI shall 1 回の一括操作で選択可能な上限件数を明示し、上限を超える選択が成立しないようにする
2. While 選択件数が上限に達している間, when ユーザーがさらに別のカードを選択しようとしたとき, the Items UI shall 上限超過を通知し、追加選択を成立させない

### NFR 3: 後方互換性

1. The Items UI shall 本要件導入後も、Issue #119 で導入された状態タブ（Unread / All / Archived）・既読トグル・アーカイブ操作・状態視覚区別の挙動を変更しない
2. The Items UI shall 本要件導入後も、Issue #115 で導入されたアクティブフィルタチップの可視化と解除動線の挙動を変更しない
3. The Items UI shall 本要件導入後も、Issue #117 で導入されたカード上タグのクリック絞り込みの挙動を変更しない
4. The Items UI shall 本要件導入後も、単一アイテムカードに既に提供されている「Delete」「Mark read」「Archive」「Refetch」「Original」操作を引き続き同等に提供する
5. The Items UI shall JavaScript を無効化したブラウザ環境で本要件導入前と同等の一覧閲覧・サイドバーフォーム送信・単一アイテム操作の動線を維持する（一括操作 UI そのものは JS 必須として未提供で構わない）

### NFR 4: アクセシビリティ

1. The Items UI shall 選択操作要素・選択ツールバー・確認ダイアログ・タグ入力欄を、キーボード操作（Tab フォーカス + Enter / Space）のみで実行可能とする
2. The Items UI shall 選択操作要素・選択ツールバーの件数・一括操作ボタン・確認ダイアログに、状態と意味が支援技術から読み取れるアクセシブルな名称（aria-label 等）を付与する
3. The Items UI shall 状態の識別を色のみに依存せず、テキストラベルまたはアイコンを併用する形で提供する

### NFR 5: 可観測性

1. The Items Service shall 一括削除および一括タグ付けの実行についてユーザー識別子・対象アイテム識別子集合・操作種別・成功／失敗内訳を構造化ログとして記録し、トークン / Cookie / 本文の生値を含めない

## Out of Scope

- ドラッグ&ドロップでの一括タグ付け（Issue #120 で別扱い）
- 一括エクスポート（CSV / JSON / OPML 等）
- 一括アーカイブ操作（Issue #119 既存の単一アーカイブ操作で代替可能。本 Issue では「一括削除」「一括タグ付け」の 2 操作に絞る）
- 一括タグ削除（特定タグを選択集合から外す操作）。本要件は「タグ付与のみ」を対象とする
- ページをまたいだ選択の保持（ページ送り後も選択を残す挙動）
- 一覧上での「全件選択」「ページ全選択」ボタン（個別選択と Shift+クリック範囲選択で代替）
- 拡張機能（Chrome Extension）側および MCP 経由での一括操作 UI / API 公開
- 一括操作の取り消し（Undo）機能
- 検索結果やタグフィルタ条件に基づく「条件一致全件選択」機能
- グローバルキーボードショートカット（範囲選択用の `Shift+Space` などキーボードのみでの範囲選択）
- 一括タグ付け入力 UI の **既存タグサジェスト機能**（typeahead / autocomplete）。本 Issue は「単一タグフリー入力」で確定し、サジェスト機能は別 Issue で扱う（旧 Open Question (b) の確定方針。design.md 設計判断 7 参照）
- 一括タグ付けでの **複数タグ同時付与**（カンマ区切り / 複数入力欄）。本 Issue は「1 リクエスト = 1 タグ」固定とし、複数タグが必要な場合はユーザーが 2 サイクル運用する。複数タグ同時付与の需要が顕在化したら別 Issue で扱う（旧 Open Question (b) の確定方針）

## Open Questions

すべての Open Questions が round 3 までに確定済みのため、現時点で未解決の項目はない。確定方針は
以下のとおりであり、各項目は **design.md の対応する設計判断と整合**している（requirements ⇄
design のスコープ確定状態を一致させる / round 2 review feedback）。

> **Note**: 旧 Open Question (a)「選択操作要素を常時表示のチェックボックスとするか、選択モード
> 切替後に表示するチェックボックスとするか」は **確定**: **常時表示のチェックボックスを採用**。
> 発見性が高く操作が 1 step 短い、棚卸し作業の主要動線で「まず選択モード ON」が常に必要だと
> 操作回数の削減効果が薄れる、カード密度の圧迫は `position: absolute` でほぼゼロにできる、
> 等を理由とする（design.md 設計判断 2 と整合）。

> **Note**: 旧 Open Question (b)「一括タグ付け入力 UI の粒度（フリー入力 / 既存タグサジェスト /
> 複数タグ同時付与）」は **確定**: **単一タグフリー入力を採用**。サジェスト機能 / 複数タグ
> 同時付与は Out of Scope に明示（design.md 設計判断 7 と整合。Out of Scope セクション末尾
> 2 行に反映済み）。

> **Note**: 旧 Open Question (c)「1 回の一括操作の上限件数（NFR 2.1）の具体数値」は **確定**:
> **100 件**。100 件超の棚卸しはサーバ側 DB トランザクション規模・確認ダイアログの心理的
> 負担の両面でユースケース不適合、100 件以下なら NFR 1.2「1 秒以内の操作完了視覚」も実測で
> 余裕、100 件超を扱いたいケースは「条件一致全件選択」機能（Out of Scope）で別 Issue 化する、
> 等を理由とする（design.md 設計判断 4 と整合）。

> **Note**: 旧 Open Question (d)「Issue 本文の仮案にあった `x` キーを選択トグル用ショートカット
> として採用するか」は **確定**: **`x` キーを採用**。既存ショートカット（`j` / `k` / `o` /
> `n` / `/` / `?` / `e`）と衝突しない、`x` は「mark for action」の慣習的な意味（多くのメーラー
> UI で選択トグル）、入力欄 focus 中は既存 handler のガード（`tag === 'INPUT'` 等）で抑止される、
> 等を理由とする（design.md 設計判断 3 と整合）。

> **Note**: 旧 Open Question (e)「一括タグ付け時の確認ダイアログを必須とするか」は **確定**:
> **不要**（一括タグ付けには確認ダイアログを設けない。削除のみ確認必須）。タグ付与は可逆操作
> （タグ削除で戻せる）でデータ消失リスクがない、タグ入力モーダルは「タグ名入力 → 確定」の
> 2 step を踏むため誤発火の心理的ハードルは確保される、仮に誤って付与してもユーザーが単一
> アイテム編集経由で外せばよい、等を理由とする（design.md 設計判断 5 と整合）。
